# 中断后保留进度与断点续跑方案

2026-10-12 更新：程序重启后不自动继续。启动 CMD 只针对最近未完成且未选择放弃的任务询问 Y/N；Y 校验后恢复原任务最近进度，N 返回初始页面，不自动新建或执行任务，并保留旧成果。下文无确认的自动恢复为历史设计，当前行为以 [当前继续规则](RESUME_ACCEPTANCE.md) 为准。

日期：2026-10-11。状态：首版续跑已落地，实际范围及验证见 [RESUME_ACCEPTANCE.md](RESUME_ACCEPTANCE.md)。本文保留完整目标方案；自动输入修复/局部失效、分布式租约、单格式补导出入口等扩展尚未实现，不能依据本文目标视为已完成。

目标：同一研究任务在网络异常、模型错误、主动暂停或进程退出后，保留已提交且有效的成果；修复问题后只执行未完成或已失效的工作，避免重新搜索、提取、分析和写作整份报告。

## 1. 当前能力与缺口

本方案基于当前仓库代码，沿用 FastAPI、SQLite、LangGraph 和单 worker，不引入分布式队列。

| 环节 | 当前实现 | 需要补齐 |
| --- | --- | --- |
| 主图 | `runner.py` 使用 `graph.sqlite` 恢复同一 `thread_id`；`graphs.py` 每个节点完成后写业务检查点 | 业务检查点与图检查点跨库提交，且备用快照仅按节点名匹配，缺少输入版本与循环执行标识 |
| 手动恢复 | `api.py` 有 cancel/resume | resume 仅接受 interrupted，failed 无入口；前端未提供暂停/继续按钮 |
| 重启 | lifespan 调度 `Store.active_runs()` | 当前连主动中断任务也会重启执行，用户暂停意图未保存 |
| 资料收集 | 来源、证据、事实可保存；提取批次支持 validated 复用与 split 重建 | Researcher 子图无独立 checkpointer；Supervisor 的 pending/摘要要整个大节点完成才返回，已完成任务可能重新检索和压缩 |
| 并行任务 | Supervisor/块分析使用 `asyncio.gather` | 某一项异常不能保证其他已成功项形成完整、可恢复的任务结果；需明确同伴收尾策略 |
| 分块分析与写作 | 块分析按输入快照复用；章节按 version 复用 | 写作草稿、Reflection、局部修订等中间步骤无完整恢复边界；现有版本键未统一涵盖提示、规则与模型配置 |
| 预测与终审 | 预测按情景/年度循环，终审按角色/章节调用 | 预测假设和各审核单元缺少执行检查点，后半程失败可能重复前面模型调用 |
| 预算 | `Gateway.attach_store()` 已从 call 记录恢复调用次数、token 预留与块预算 | 请求发送前未持久化预留，硬退出可能漏账；成功调用后的内存 token 调整与保存字段口径也需统一 |
| 阶段成果 | v1.2 有固定快照预览、JSON/Markdown/ZIP 导出 | 评估材料是尽力写入，不能直接当作可执行恢复状态 |
| 启动器 | `scripts/start.ps1` 在 Chrome 应用窗口关闭后停止本次服务 | 正常关闭须保存暂停意图并给已发请求收尾时间；强制退出走崩溃恢复 |

已有功能说明了恢复基础已经具备。主要改造方向是：把大节点内部的昂贵步骤变成独立提交的工作单元，并将“已保存材料”与“可安全复用结果”区分开。

## 2. 用户行为与页面

在现有研究进度区增加操作，不新增历史管理页面。

| 状态/场景 | 页面行为 |
| --- | --- |
| 运行中 | 显示“暂停研究”，点击后显示“正在保存进度”；阶段成果仍可查看 |
| 已暂停 | 显示“继续研究”，说明已保存的任务、批次、分析块、章节数量与恢复位置 |
| 执行失败且可恢复 | 显示“从断点继续”、失败原因及需要修复的配置/网络问题 |
| 预算耗尽 | 显示累计用量、剩余额度及“增加预算后继续”；不自动重置预算 |
| 审核/数据阻断 | 显示阻断原因及修复要求；修复输入后才提供“修复后继续” |
| 检查点不兼容或损坏 | 明确提示恢复不可用及原因，保留“查看阶段成果/导出评估包” |
| SSE/浏览器连接断开 | 提示连接状态并重连；不把断线当作后端任务暂停 |

示例文案：“已保存 12/15 个研究任务、8 个分析块、6 个章节。继续后将从剩余 3 个研究任务开始；已完成且版本有效的成果将复用。”以上数字是展示示例，实际由工作单元清单生成，不由事件日志猜测。

“重新开始”创建新 run_id，旧任务与成果保留。恢复沿用原 run_id、来源引用和历史事件，每次恢复建立新的 attempt_id。

刷新后仍定位原任务。继续研究后前端必须重新建立 SSE 和状态轮询：当前 hook 只依赖 id，同一 run_id 从终态恢复不会自动触发 effect。新增 connection_epoch，在 resume 成功后递增；保留去重后的事件并从已知事件游标继续接收，清理上一轮错误和过期运行中提示。

## 3. 恢复规则与状态

沿用 queued/running/interrupted/failed/blocked/completed/limited，增加 pausing。interrupted 在页面显示“已暂停”，同时持久化 stop_reason、resume_policy、resume_count、last_attempt_id。

- 运行 → pausing → interrupted：主动暂停，默认仅用户操作后恢复。
- failed → queued → running：恢复前校验通过，再从断点执行。
- blocked → queued → running：输入修复完成，并已计算失效范围后执行。
- 进程崩溃遗留的 running/pausing：启动时先识别无有效执行者；running 按保存的恢复策略处理，pausing 完成暂停，不能重新开工。
- completed/limited 不支持默认续跑；仅缺失可选导出文件可单独重建，不重跑研究。

恢复能力与业务状态分开。新增 recovery_state：ready / action_required / unavailable，以及 error_code、failed_unit_id、recovery_action。具体分类：

| 原因 | 处理方式 |
| --- | --- |
| 短暂网络/429/5xx | Gateway 有界重试；耗尽后保存断点，可手动继续 |
| 密钥、地址、模型配置错误 | 修复配置后重检，复用未受影响成果 |
| JSON/结构校验/输出截断 | 已提交结果保留；失败单元按拆分/定向修复策略执行，不反复发送同一超大请求 |
| 预算耗尽 | 增加原任务总预算上限后继续，保留原累计成本和修复次数 |
| 财务缺口、引用问题、质量不达标 | 原 blocked 保留；补资料/修改输入后仅失效依赖后代，质量门槛照常执行 |
| 未知异常 | 默认 action_required；修复部署后做兼容性检查，不能宣称一定可恢复 |
| 旧规则/无法解析的状态 | unavailable；保留评估出口，不拼接不兼容上下文 |

自动重试次数、补查轮数、拆批次数、反思/终审修订次数跨恢复累计，不能用重复点击继续绕过上限。

## 4. 保存粒度

主图仍负责阶段路由，工作单元台账负责大节点内的恢复。长节点内部只从台账加载当前输入版本已成功提交的结果；事件和进度百分比仅用于展示。

| 工作单元 | 标识与需要保存的结果 |
| --- | --- |
| 识别/规划/修复 | 每次结构化调用及验证步骤；保存候选结果、校验问题和剩余修复次数 |
| 搜索/来源读取 | task_id + round + query/source 指纹；保存本次结果集合及来源版本，恢复不依赖会过期的通用缓存 |
| Researcher | task_id + research_generation + round + retrieve/extract/gap/compress；保存状态增量与轮次，完成后提交完整 task_output |
| 提取批次 | batch_id + 输入指纹；父子拆分结构、有效输出、隔离结果分别保存 |
| 分块分析 | block_id + 输入快照；保存回答与验证状态，复用现有 block_analysis 能力 |
| 预测假设 | scenario + period + 输入指纹；保存假设、模型选择、限制与验证结果 |
| 三表计算 | scenario + year + 上一年结果版本；保存结果和下一年需要的滚动余额/引用 |
| 章节写作 | section_id + 输入指纹 + draft/reflection/revision/resolve；保存完整草稿、反思输出、修订稿和最终章节 |
| 终审 | report_snapshot_id + reviewer + section_id + 审核规则版本；保存各单元意见，只执行缺失审核 |
| 渲染 | approved_snapshot_id + format + 渲染版本；已提交且校验正确的格式复用，失败格式单独重试 |

成本收益优先级：完整研究任务、预测假设、写作子步骤、语义审核单元优先于廉价的确定性计算。第一阶段不承诺续接一条未完成的模型输出；只能保留已经完整返回并提交的结果。

并行任务独立提交。收集每项结果，单项失败后停止启动新的依赖任务，让已发出的同伴完成并提交，最后记录失败集合。仅重新调度失败/未执行项；成功任务不会因同批某一任务失败而被丢弃。收尾超时后取消仍未完成项，标记 uncertain，而不是 succeeded。

Supervisor 的 pending 从当前 generation 的任务台账重建，摘要/事实按稳定 ID 去重。研究任务完成与分析块依赖就绪分别计算，避免同一个块内只完成一个任务就释放下游。不能直接拿 records 中的 task 规划记录当作执行成功标记。

## 5. 持久化与一致性

在现有业务 SQLite 中增表，graph.sqlite 保留。恢复核心写入必须成功，否则停止并报告保存失败；不采用评估旁路的“尽力写入”。

| 表 | 关键字段与职责 |
| --- | --- |
| execution_attempts | attempt_id、run_id、trigger、started_at、ended_at、status、executor_epoch；追踪每次执行与恢复 |
| execution_units | run_id、unit_key、generation、input_fingerprint、state、output、output_hash、dependency_versions、attempt_count、executor_epoch；保存可复用结果 |
| execution_failures | failure_id、unit_key、attempt_id、error_code、sanitized_message、recovery_action；追加失败历史 |
| call_ledger | call_id、attempt_id、unit_key、request_fingerprint、reserved_tokens、actual_usage、state；请求前预留并累计预算 |
| run_control | run_id、pause_requested、resume_policy、executor_epoch、heartbeat_at、budget_limits、control_revision；原子控制与并发保护 |

工作单元状态：pending → running → succeeded；异常进入 failed，失去执行者进入 uncertain，输入变化进入 stale。另存 validation_state（verified/quarantined 等），不将执行结束等同于质量通过。

unit_key = 节点/任务/轮次/子步骤，generation 区分补查和修订。复用键包含 input_fingerprint，台账唯一约束覆盖 run_id + unit_key + generation + input_fingerprint，保留旧版本记录。不能只按 node 名匹配：supervisor/revise 等节点在循环中会重复出现。

提交协议：

1. 原子校验执行者 epoch、暂停意图和预算，领取单元；外部调用前持久化 call_id 与预算预留。
2. 返回结果后完成结构/引用等校验；同一业务事务提交单元输出、引用材料、预算结算、成功状态与进度事件。校验失败保留完整响应供修复，但不能进入有效成果集合。
3. 将已提交结果合并到图上下文，由 LangGraph 写图检查点。
4. 若第 2 步成功、第 3 步前退出，图重放该单元时命中台账，直接合并结果，不再调用外部服务。
5. 若第 2 步未提交，单元保持未完成/uncertain；恢复后最多重试该单元，其余已提交成果继续复用。

图检查点决定控制流，业务台账决定工作结果是否可复用。业务层不根据“最后节点名”自行跳过一串主图节点；在图需要重放时，按执行实例和输入版本复用。旧的单节点备用检查点需要加执行标识校验，或仅在可靠匹配时使用。

graph.sqlite 缺失/损坏时不能悄悄从 START 重跑。首期提示 unavailable 并保留阶段成果；后续若支持重建，必须从已验证路由状态、循环计数与完整依赖链重建。备份须协调两库及引用文件，保存恢复清单与版本，不能随手分别复制运行中的数据库。

导出先写临时文件，校验完成后原子替换正式文件，再登记 hash/size/snapshot。线程中的文件渲染被取消不一定立即终止，使用 epoch 隔离临时路径与提交权，禁止旧执行者覆盖新结果。

## 6. 输入版本与局部失效

input_fingerprint 使用确定性的规范化结构计算，至少涵盖：公司、Brief/研究截止时间、任务与问题、来源内容哈希、所选事实/假设/计算/上游结论版本、提示版本、schema、公式/审核规则版本及相关模型协议/名称/采样参数。集合排序后计算，避免顺序变化造成无意义重算。

- 默认继续冻结原研究的 as_of 与已保存来源，不因为隔了一天就自动扩大研究范围。
- 通用搜索缓存 TTL 到期不删除该任务已提交的来源与检索结果。
- 密钥/凭证更换不使内容失效；模型、提示、公式与资料变化只影响消费它们的单元及依赖后代。
- 降低预算不能抹掉历史消耗；增加预算不让成果失效。并发、超时等执行参数一般不影响已验证内容。
- 新增来源/修正事实属于输入修复事务：保存新版本与来源关系，计算 stale 闭包，更新目标恢复位置，再允许调度。
- 涉及 Brief/计划结构重建时提升 research_generation；旧任务 ID 和旧 pending 不混用。
- 报告内容变化时撤销旧快照的交付资格；未变化审核可作为历史记录保留，最终批准必须覆盖当前完整 report_snapshot_id。

恢复计划先计算失效范围，再选择控制流入口。无输入变化时使用当前图的 next；有变化时从最早受影响阶段之前的兼容状态建立新 generation，执行既有依赖与条件路由，期间逐单元命中仍有效的台账。必须持久化这次路由修订与循环计数；不能仅把台账标成 stale，却仍从旧的 render/deliver 入口继续。首期只开放有明确回退入口的资料、配置和预算修复，不支持任意手工编辑图状态。

例如修复 F03 现金流事实：保留公司介绍和独立行业材料，重新计算 F03 及消费其结果的预测/业务/估值/风险/综合链；是否影响某块由实际 dependency_versions 判断。价格等时效数据若要更新，作为明确的新输入版本处理。

## 7. 预算与无法消除的重复边界

所有 attempt 共用 run 的调用次数、块预算和 token 预算。call_ledger 请求前原子预留，响应后按供应商 usage 结算；usage 缺失或请求结果未知则保守保留预留，展示“用量未知/估算”。用相同 call_id 结算，避免重复入账；不把预留与实际用量同时累加。

call_id 唯一且追加保存。脱敏调用元数据与可复用结果分开保存，内部恢复数据不通过阶段包暴露系统提示、凭证或隐藏推理。

必须明确保证边界：外部模型已经完成计费、但响应尚未在本地提交就崩溃时，可能重复该次请求。仅当供应商实际支持幂等键或结果查询时才使用这些能力；不能宣称任意模型调用“恰好执行一次”。预期保证是已成功提交且输入有效的单元不再重复调用。

预算调整为明确动作，保存调整前后限额与原因。增加额度只解除预算阻断，不重置补查/修订上限；如需增加修复次数也必须单独记录。

## 8. 暂停、重启与调度

默认暂停采用“停止接新工作、完成已发请求、保存结果”模式，建议收尾上限 60 秒。后端收到暂停请求先写 pause_requested，再反馈 pausing；各工作单元领取前、模型重试前及工具轮次边界检查该标志。

正在执行的请求完成后提交结果，不启动新的 Reflection/下一年预测/下游工作。上限耗尽时取消未完成请求，标为 uncertain，任务进入 interrupted。排队任务直接暂停，无需调用模型。页面说明“已发出的请求仍可能完成并计费”。

正常服务退出与启动器关闭尽量调用同一收尾逻辑；硬杀进程只能恢复已持久化成果。启动器在终止服务前等待收尾，不以浏览器 SSE 断开触发暂停。

重启策略：主动暂停永不自动继续；崩溃遗留 running 在兼容性与预算通过后按持久化 resume_policy 恢复，默认可沿用现有自动恢复行为；failed/blocked 等待修复与显式继续。队列容量仅统计 queued/running/pausing，不把历史 interrupted 算作活跃队列。

保持单 worker。schedule 和 resume 增加数据库条件更新及 executor_epoch，防止双击、多标签页和旧回调重复调度；只有当前 epoch 能提交结果/修改状态。任务完成回调仅清理自身对应 task。现有 `tasks` 字典可保留作本进程管理，但不能是唯一防重依据。

## 9. 接口合同

| 接口 | 合同 |
| --- | --- |
| GET /api/research/{id} | 增加 recovery_state、stop_reason、failed_unit、resume_count、progress_counts、budget_summary、control_revision |
| GET /api/research/{id}/recovery | 只读恢复计划：恢复位置、复用/剩余/失效项数量、所需动作、兼容性结果；不调用模型、不执行研究 |
| POST /api/research/{id}/pause | 幂等请求暂停，返回 202 与 pausing/interrupted；排队任务直接 interrupted |
| POST /api/research/{id}/cancel | 保留为 pause 的兼容别名；响应文案统一 |
| POST /api/research/{id}/resume | 原子校验后返回 202，沿用 run_id 并返回 attempt_id；重复同一请求不重复调度 |
| POST /api/research/{id}/budget | 更新任务总预算，保留消费记录；返回新恢复计划，不自动调度 |

resume 请求可携带 expected_control_revision 与 idempotency_key；相同幂等键返回原 attempt，过期版本或不可恢复返回 409/明确原因，队列满返回 429。先完成校验和状态事务，再调度；不得先清空错误、设 running 再检查能否恢复。

只读 recovery 可先使用 persisted error_code 返回 action_required；用户执行继续前，后端再检查实际配置与可用额度。检查配置不必发送付费探测调用。

首期复用现有本地资料配置作为输入修复来源，增加后端服务层 `apply_input_revision` 处理资料变化和失效事务；恢复前显示修复影响。文件上传/编辑工具可后续扩展。blocked 的恢复必须经过该修复链，不能简单开放现有 resume 状态白名单就跳过质量阻断。

## 10. 实施拆分

| 阶段 | 修改位置 | 交付内容 |
| --- | --- | --- |
| A：可见续跑入口 | schemas.py、storage.py、api.py、runner.py；frontend api/types/useResearch/App | 状态分类、failed 恢复、主动暂停不被启动恢复、幂等调度、恢复信息与 SSE 重连；保持节点粒度保证 |
| B：减少主要重复调用 | 新 execution.py；graphs.py、researcher.py、writers.py、reviewers.py | 工作单元事务、研究任务/批次/预测假设/写作子步骤/审核的完整结果复用；正确合并并行结果 |
| C：崩溃与成本一致性 | llm.py、storage.py、runner.py、渲染与启动脚本 | 请求前预算台账、输入版本/局部失效、epoch、防跨库窗口重复、原子导出、退出收尾与故障注入验收 |

A 能解决“失败没有继续入口”，但 B/C 完成前不能承诺大节点内所有已付费工作均被保留。建议 A+B+C 作为首个完整验收版本，分阶段提交验证。分布式执行、跨任务通用结果缓存、模型流式输出续接暂不纳入。

## 11. 验收标准

测试使用隔离数据库与 Mock HTTP，对外调用计数按单元指纹统计；必须通过真实 kill/restart 覆盖硬退出，不能只以 asyncio 取消测试替代。无须消耗真实模型额度。

| 场景 | 必须满足 |
| --- | --- |
| 主图节点后退出 | 同一 run_id 继续；已有节点有效输出不重复调用 |
| 业务结果提交后、图 checkpoint 前退出 | 图重放命中台账；该单元外部调用计数不增加 |
| 多项研究任务完成后某项失败 | 已成功任务不重新搜索/提取/压缩；失败与未执行项继续 |
| 提取拆批中断 | 已验证子批次复用，父批次不重新调用；轮次及拆分次数不重置 |
| 9 组假设完成 7 组后退出 | 只调用剩余 2 组；假设跨情景/年份校验保持有效 |
| 草稿完成、Reflection 失败 | 复用草稿，只重试 Reflection；修订中断同理 |
| 某 reviewer/章节失败 | 当前快照已完成审核不重复；剩余审核成功后才汇总批准 |
| DOCX 完成、PDF 失败 | 复用有效 DOCX 与批准报告，仅重试 PDF |
| 用户暂停后重启服务 | 保持 interrupted，无新增模型/搜索调用 |
| 双击继续/多标签页 | 仅一个有效 attempt 执行，不重复扣预算或提交成果 |
| 预算耗尽后恢复 | 未追加预算时不调用；增加总限额后累计消费不减少 |
| 请求发出后硬退出 | call_ledger 有预留、标为 uncertain；显示可能重复调用的范围 |
| 修正资料或切换模型 | 仅相关单元与依赖后代 stale；旧批准不能交付新报告 |
| 检查点损坏/旧版本 | 保留原成果、明确不可恢复原因，不暗中重新全量研究 |
| 前端终态后继续 | SSE/轮询重新工作；原进度保留，旧 active 提示被正确关闭 |
| blocked 修复后继续 | 未修复时保持阻断；修复后局部重算且执行原审核门槛 |

核心指标：输入与配置不变时，恢复过程对已经成功提交的外部调用单元，重复调用数为 0；所有执行 attempt 的累计预算有账可查；进度不因恢复清零；任何质量门槛均不因继续操作被绕过。

对没有台账的旧任务，仅保证现有完整节点检查点、可验证的 batch/block_analysis/section 复用；无法证明版本和完整性的材料保留供评估，不伪造完整执行历史。迁移增表与字段默认值，保留原成果；旧规则检查点仍按现有兼容限制处理。
