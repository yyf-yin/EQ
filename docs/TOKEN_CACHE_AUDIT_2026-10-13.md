# 模型输入、缓存与短请求诊断

检查对象：贵州茅台研究任务 `d79f32312a5542fcab30576535d99b41`。只读分析原调用、实际发送资料包和断点，并以模拟响应重放容量拆分；未为诊断调用真实模型。

最近 100 次成功调用实际输入中位数 **4601.5 token**，保守输入估算中位数 **13719**，实际输出中位数 **187 token**，请求耗时中位数 **2.828 秒**。估算算法返回完整 JSON 的 UTF-8 字节数，是容量上界，不是模型 tokenizer 的精确计数。预算结算使用供应商实际输入加输出；未知请求才保留预留。

这些调用全部属于上传资料的问题覆盖检查，78 次得到 `covered: {}`。它们判断一小包证据能否覆盖研究问题，输出很短；时间表示一次 HTTP 请求及接收处理，不能当作整项研究完成时间，也不能据此断言模型没有阅读或思考。当前请求未显式指定思考开关，历史记录未保存独立 reasoning 用量，无法还原每次实际思考量。DeepSeek 当前文档说明默认开启思考；因此不能将短响应直接归因于关闭思考。[官方思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)

已确认的输入浪费：历史覆盖检查存有 **3218 个发送资料包**，序列化内容约 3677 万字节，其中约 **2171 万字节（59.0%）** 是反复附带的整份 PDF 页码列表。每个包的证据数量中位数只有 3 条、财务事实只有 2 条。所有资料重复进入覆盖检查，并受研究员 20000 字节保守输入上限约束，产生大量小请求。

历史调用没有缓存命中/未命中字段，无法用本地数据核实用户在供应商后台观察到的低命中率。DeepSeek 的缓存依赖相同输入前缀，重复内容位于变化内容之后不保证命中；不同证据包会改变大量输入。缓存比例低也不直接等于响应速度异常。[官方缓存说明](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)
